# Price Control V3 — карта данных

Версия документа: 0.1

Этот файл объясняет простым языком, какие данные используются в Price Control V3,
откуда они берутся, где хранятся и как связаны между собой.

Документ предназначен не только для программистов.

> Важно:
> Price Control V2 является действующей рабочей системой и не изменяется.
> Price Control V3 разрабатывается как отдельный проект.

---

# 1. Общая задача Price Control V3

Price Control V3 должен полностью отказаться от использования Google Sheets
в качестве рабочего хранилища данных.

Основное хранилище:

PostgreSQL

Пользователь работает через веб-интерфейс:

React

Серверная часть:

Node.js + Express

Общая схема:

Пользователь
↓
React
↓
Express API
↓
PostgreSQL

Парсеры поставщиков также работают через сервер и записывают результаты
не в Google Sheets, а непосредственно в PostgreSQL.

---

# 2. Основные группы данных

В существующей системе имеются три основные группы данных:

1. ГЭСН
2. МАТ ГЭСН
3. Поставщики и результаты парсинга цен

В Price Control V3 эти данные сохраняются, но структура хранения меняется.

---

# 3. ГЭСН

## 3.1. Что это

ГЭСН — основная база расценок.

Исходные данные сейчас находятся на листе:

ГЭСН

в существующей Google Таблице / Excel-файле базы цен.

Лист имеет блочную структуру.

Один блок может содержать:

Расценку ГЭСН
↓
состав работ
↓
материалы и ресурсы этой расценки

То есть одна строка Excel не всегда является отдельной расценкой.

---

# 4. Как ГЭСН планируется хранить в PostgreSQL

Предварительное решение:

одна основная таблица

gesn_rows

Одна запись PostgreSQL соответствует одной логической строке существующего листа ГЭСН.

Для определения назначения строки используется поле:

row_type

Предварительные типы:

RATE
WORK_STEP
MATERIAL

RATE — строка самой расценки.

WORK_STEP — строка состава работ.

MATERIAL — материал или ресурс, относящийся к расценке.

---

# 5. Связь строк внутри ГЭСН

Строки состава работ и материалов должны знать,
к какой расценке они относятся.

Для этого используется внутренняя связь:

parent_rate_id

Пример:

ГЭСН01-01-...
Разработка грунта
|
+-- состав работ №1
+-- состав работ №2
+-- материал №1
+-- материал №2

Все эти данные физически находятся в таблице gesn_rows,
но связаны между собой внутренними ID PostgreSQL.

---

# 6. Почему ГЭСН пока решено хранить одной таблицей

Рассматривался вариант разделения ГЭСН на три таблицы:

gesn_rates
gesn_work_steps
gesn_rate_materials

На текущем этапе от этого варианта отказались.

Причины:

1. Нужно сохранить понятную связь с существующим листом ГЭСН.
2. Важно облегчить первоначальный перенос данных.
3. Важно облегчить последующий импорт и экспорт Excel.
4. Объём ГЭСН небольшой для PostgreSQL и не создаёт проблемы производительности.
5. Для пользователя структура должна оставаться понятной.

При необходимости PostgreSQL позволит создать представления:

v_gesn_rates
v_gesn_work_steps
v_gesn_materials

Они будут показывать отдельные типы строк,
но физического дублирования данных не будет.

---

# 7. МАТ ГЭСН

## 7.1. Что это

МАТ ГЭСН — основной каталог материалов и ресурсов,
который используется Price Control.

Исходные данные сейчас находятся на листе:

МАТ ГЭСН

Каждый материал может содержать:

- код ресурса;
- официальное наименование;
- единицу измерения;
- количество или множитель;
- признаки проверки;
- поставщиков;
- ссылки на карточки товаров;
- цены;
- даты обновления;
- служебные данные.

---

# 8. Как МАТ ГЭСН планируется хранить

Основная таблица:

materials

Она хранит сам материал.

Предварительно:

id
resource_code
official_name
base_quantity
base_unit
verified
notes
created_at
updated_at

id — внутренний уникальный идентификатор PostgreSQL.

Код ресурса не является внутренним ID базы.

---

# 9. Дубли материалов

В существующих данных возможны повторяющиеся:

- коды ресурсов;
- коды + наименования.

Кроме того, существующая бизнес-логика Price Control
в отдельных операциях специально допускает добавление дублей.

Поэтому на текущем этапе запрещено устанавливать:

UNIQUE(resource_code)

или:

UNIQUE(resource_code, official_name)

Каждая запись получает собственный внутренний id.

# 10. Поставщики

Поставщик — строительный магазин или другая организация,
на сайте которой снабженец нашёл подходящий материал.

Примеры:

Петрович
ЭТМ
TINKO
SATURN
Строительный двор
и другие.

Список поставщиков хранится отдельно:

suppliers

Предварительно:

id
code
name
parser_key
enabled

---

# 11. URL товара — критически важные данные

URL нельзя удалять из системы.

Существующая рабочая логика:

Снабженец находит требуемый материал
↓
находит подходящий товар в строительном магазине
↓
указывает поставщика
↓
вставляет URL карточки товара
↓
Price Control сохраняет этот URL
↓
парсер открывает именно этот URL
↓
получает актуальную цену
↓
результат записывается в базу

Поэтому поставщик и URL являются одной из основных частей Price Control.

---

# 12. Почему URL не хранится непосредственно в materials

Один материал может иметь несколько поставщиков.

Например:

Материал №1258
|
+-- Петрович → URL №1
+-- ЭТМ → URL №2
+-- Сатурн → URL №3

Поэтому сам материал хранится в:

materials

а карточки магазинов хранятся отдельно в:

supplier_offers

# 14. Несколько поставщиков одного материала

В Google Sheets количество альтернативных поставщиков
ограничено структурой колонок.

В PostgreSQL такого ограничения не будет.

Один материал сможет иметь:

1 поставщика
3 поставщика
10 поставщиков
и более.

Поле priority определяет порядок предпочтения.

# 15. Парсинг цен

Парсер получает из базы:

поставщика

- URL товара
- настройки товара

После этого:

URL
↓
парсер поставщика
↓
сайт магазина
↓
получение цены
↓
нормализация цены
↓
PostgreSQL

Google Sheets в этой цепочке в Price Control V3 использоваться не должен.

---

# 16. История цен

Price Control V3 должен сохранять не только последнюю цену,
но и историю изменений.

Для этого планируется таблица:

supplier_price_history

Пример:

01.09.2026 — 1 250 руб.
05.09.2026 — 1 310 руб.
10.09.2026 — 1 275 руб.

Это позволит:

- видеть изменение цены;
- находить ошибки парсинга;
- анализировать актуальность цены;
- восстанавливать состояние на прошлую дату.

---

# 17. Пересчёт единиц измерения

Цена магазина и цена сборника могут относиться
к разным единицам или упаковкам.

Например:

магазин продаёт упаковку 1,5 м2
цена упаковки 1019 руб.

Price Control должен получить цену за 1 м2.

Для этого будет использоваться коэффициент пересчёта:

conversion_factor

Логику существующих Excel-формул необходимо перенести
в программные правила Price Control V3.

Формулы Google Sheets хранить в PostgreSQL не требуется.

# 18. Связь ГЭСН и МАТ ГЭСН

В существующей системе значительная часть связей выполняется

Предварительная схема:

Это позволяет изменить наименование материала,
не разрушив связь с ГЭСН.

# 26. Решение по хранению текущих цен

Утверждено использовать следующий подход:

Текущие рабочие цены хранятся непосредственно в:

supplier_offers

История изменения цен будет храниться отдельно в:

supplier_price_history

---

## 26.1. Зачем текущая цена хранится в supplier_offers

Price Control постоянно использует актуальную цену:

- при отображении материалов;
- при работе снабженца;
- при расчёте смет;
- при сравнении цен;
- при проверке результатов парсинга.

Поэтому текущая цена должна быть доступна напрямую,
без необходимости каждый раз искать последнюю запись
в истории изменения цен.

---

## 26.2. Какие текущие цены будут храниться

Предварительно в supplier_offers используются два отдельных значения:

approved_price

и

last_parsed_price

approved_price — текущая рабочая цена,
которая считается принятой для использования Price Control.

last_parsed_price — последняя цена,
которую автоматически получил парсер с сайта поставщика.

Эти значения могут отличаться.

Пример:

approved_price = 1250

last_parsed_price = 1310

Это означает:

парсер уже обнаружил новую цену 1310,
но рабочей подтвержденной ценой пока остаётся 1250.

Такой подход позволит в будущем организовать
ручную проверку изменения цены снабженцем.

---

## 26.3. Даты цен

Для текущих цен планируются поля:

approved_at

last_parsed_at

approved_at — когда рабочая цена была подтверждена.

last_parsed_at — когда парсер последний раз получил цену с сайта.

---

## 26.4. История цен

Каждый результат парсинга в дальнейшем должен сохраняться
в отдельной таблице:

supplier_price_history

Таким образом изменение:

1250
↓
1310
↓
1275

не уничтожает предыдущие значения.

В supplier_offers находится только текущее состояние.

В supplier_price_history находится история.

---

## 26.5. Общая схема

supplier_offers

хранит:

материал

- поставщик
- URL
- настройки парсинга
- текущая подтвержденная цена
- последняя полученная парсером цена

↓

supplier_price_history

хранит:

все результаты изменения цены во времени

## 28. Первый рабочий CRUD-модуль материалов

На 01.09.2026 в Price Control V3 реализован и вручную проверен первый полный цикл работы с материалами через веб-интерфейс.

CRUD включает четыре основные операции:

- **Create** — создание новой записи;
- **Read** — чтение существующих записей;
- **Update** — изменение существующей записи;
- **Delete** — удаление записи.

### 28.1. Общая схема работы

Пользователь работает с материалами через React-интерфейс.

React напрямую к PostgreSQL не подключается.

Обмен данными выполняется по цепочке:

```text
Пользователь
    ↓
React
    ↓
Express API
    ↓
PostgreSQL
    ↓
Express API
    ↓
React
```

PostgreSQL является центральным источником данных.

React отвечает за интерфейс пользователя.

Express отвечает за приём запросов от React, проверку данных и обращение к PostgreSQL.

---

### 28.2. Чтение материалов — READ

Для получения списка материалов используется API:

```text
GET /api/materials
```

Backend получает записи из таблицы PostgreSQL:

```text
materials
```

Общая схема:

```text
React
    ↓
GET /api/materials
    ↓
Express
    ↓
SELECT из таблицы materials
    ↓
PostgreSQL
    ↓
Express возвращает JSON
    ↓
React отображает таблицу
```

Проверено:

- React получает реальные данные из PostgreSQL;
- русский текст корректно отображается в браузере;
- булево поле `verified` отображается пользователю как «Да» или «Нет»;
- после изменений React может повторно загрузить актуальное состояние базы.

---

### 28.3. Создание материала — CREATE

Для создания нового материала используется API:

```text
POST /api/materials
```

Пользователь заполняет форму «Добавить материал» в React.

В форму входят:

- код ресурса;
- наименование;
- количество;
- единица измерения;
- признак «Материал проверен»;
- примечание.

После нажатия кнопки «Добавить материал» выполняется:

```text
React
    ↓
POST /api/materials
    ↓
Express
    ↓
INSERT INTO materials
    ↓
PostgreSQL
    ↓
новая запись
    ↓
повторный GET /api/materials
    ↓
React показывает новую строку
```

Создание через React было проверено вручную.

Тестовая запись была успешно создана и затем отдельно найдена непосредственно в PostgreSQL.

---

### 28.4. Изменение материала — UPDATE

Для изменения существующего материала используется API:

```text
PATCH /api/materials/:id
```

Пример:

```text
PATCH /api/materials/1
```

Пользователь нажимает кнопку «Изменить».

После этого значения выбранной строки становятся редактируемыми.

До нажатия кнопки «Сохранить» изменения существуют только в React и PostgreSQL не изменяется.

После нажатия «Сохранить»:

```text
React
    ↓
PATCH /api/materials/:id
    ↓
Express
    ↓
UPDATE materials
    ↓
PostgreSQL
    ↓
повторный GET /api/materials
    ↓
React показывает сохранённые данные
```

Проверено:

- изменение наименования;
- изменение примечания;
- изменение признака `verified`;
- корректная запись русского текста;
- изменение поля `updated_at`;
- сохранение изменений непосредственно в PostgreSQL.

Также реализована кнопка «Отмена».

При нажатии «Отмена» несохранённые изменения отбрасываются, а PostgreSQL не изменяется.

---

### 28.5. Удаление материала — DELETE

Для удаления материала используется API:

```text
DELETE /api/materials/:id
```

Пример:

```text
DELETE /api/materials/4
```

Удаление является необратимой операцией, поэтому React сначала показывает пользователю окно подтверждения.

В окне подтверждения отображается наименование материала.

Если пользователь нажимает «Отмена»:

```text
DELETE-запрос не отправляется
PostgreSQL не изменяется
```

Если пользователь подтверждает удаление:

```text
React
    ↓
DELETE /api/materials/:id
    ↓
Express
    ↓
DELETE FROM materials
    ↓
PostgreSQL
    ↓
повторный GET /api/materials
    ↓
удалённая строка исчезает из React
```

Удаление было проверено:

- через отдельный тестовый API-запрос;
- через кнопку «Удалить» в React;
- прямым SELECT-запросом к PostgreSQL после удаления.

Подтверждено, что удаляется только выбранная запись.

### 28.6. Repository для работы с материалами

SQL-логика работы с таблицей `materials` вынесена из `server.js` в отдельный файл:

```text

```

В repository находятся функции:

```text

createMaterial()
updateMaterial()
deleteMaterial()
```

Назначение функций:

- `getMaterials()` — получает материалы из PostgreSQL;
- `createMaterial()` — создаёт новую запись;

Такое разделение используется для того, чтобы:

- HTTP-логика Express не смешивалась с SQL;
- код было проще читать;
- работу с PostgreSQL можно было развивать отдельно;
- в дальнейшем было проще добавлять новые таблицы и модули.

## 29. Миграция листа «МАТ ГЭСН» в PostgreSQL

### 29.1. Назначение листа «МАТ ГЭСН»

Лист `МАТ ГЭСН` в старой системе является основной базой материалов и цен.

В нём одновременно хранятся:

- код ресурса;
- нормативное наименование материала;
- единица измерения сборника;
- информация о товаре поставщика;
- количество товара/упаковки поставщика;
- цена товара на сайте;
- цена, полученная парсером;
- пересчитанная цена за единицу измерения сборника;
- URL товара;
- признак участия в автоматическом парсинге;
- даты обновления цен;
- технические примечания;
- признак проверки материала;
- ссылки на второго и третьего поставщика.

В Price Control V3 эти данные больше не должны храниться в одной плоской таблице.

Они разделяются между:

- `materials` — сам материал;
- `suppliers` — справочник поставщиков;
- `supplier_offers` — конкретные предложения и цены поставщиков.

---

### 29.2. Основной принцип переноса

Одна строка старого листа `МАТ ГЭСН` создаёт:

1. одну запись в `materials`;
2. ноль, одну или несколько записей в `supplier_offers`.

При этом:

- одинаковые коды ресурсов автоматически не объединяются;
- одинаковые код + наименование автоматически не объединяются;
- номер исходной строки Excel сохраняется в `legacy_row_number`;
- данные не исправляются автоматически по догадке;
- некорректные значения должны попадать в отчёт импорта;
- исходный Excel при импорте не изменяется.

---

### 29.3. Почему код ресурса не является уникальным ключом

Анализ исходного файла показал большое количество повторяющихся кодов ресурсов.

Поэтому:

```text
materials.resource_code
```

НЕ имеет ограничения `UNIQUE`.

Для связи внутри PostgreSQL используется внутренний:

```text
materials.id
```

Это стабильный первичный ключ V3.

Исходный код ресурса остаётся бизнес-атрибутом материала, но не используется как единственный идентификатор записи.

---

### 29.4. Соответствие колонок Excel и таблицы materials

Основное соответствие:

| Excel              | Значение                   | PostgreSQL                    |
| ------------------ | -------------------------- | ----------------------------- |
| A                  | Код ресурса                | `materials.resource_code`     |
| B                  | Наименование базы          | `materials.official_name`     |
| D                  | Количество единиц сборника | `materials.base_quantity`     |
| E                  | Единица измерения сборника | `materials.base_unit`         |
| Q                  | Материал проверен = 1      | `materials.verified`          |
| номер строки Excel | исходное положение         | `materials.legacy_row_number` |

Пример:

```text
A = 01.1.01.09-0021
B = Шнур асбестовый...
D = 1
E = кг
Q = 1
```

в PostgreSQL становится приблизительно:

```text
materials
--------------------------------
resource_code      = 01.1.01.09-0021
official_name      = Шнур асбестовый...
base_quantity      = 1
base_unit          = кг
verified           = true
legacy_row_number  = номер строки Excel
```

---

### 29.5. Правило для признака «Материал проверен»

Старая колонка:

```text
Q — Материал проверен = 1
```

переносится в:

```text
materials.verified
```

Правило:

```text
Q = 1
    → verified = true

Q пусто
    → verified = false
```

---

### 29.6. Проблемные значения D и E

В исходном Excel встречаются строки, в которых колонка D содержит не число, а текстовое значение единицы измерения, например:

```text
т
шт
```

Также существуют отдельные строки:

```text
D заполнено
E пусто
```

Импортёр НЕ должен самостоятельно угадывать правильное значение.

Правило импорта:

```text
если D корректное число
    → записать в base_quantity

если D некорректно
    → base_quantity = NULL
    → записать проблему в отчёт импорта
```

Если отсутствует `base_unit`, оно также не должно автоматически восстанавливаться по предположению.

---

### 29.7. Строка без наименования

В исходной базе существует как минимум одна строка:

```text
resource_code есть
official_name отсутствует
```

При этом:

```text
materials.official_name
```

в PostgreSQL является обязательным полем `NOT NULL`.

Поэтому такая строка не должна получать придуманное название.

Импортёр должен:

1. зафиксировать строку в отчёте;
2. не создавать некорректную запись `materials`;
3. продолжить обработку остальных строк.

Одна повреждённая строка не должна останавливать импорт всей базы.

## 29.8. Основное предложение поставщика

Основное предложение хранится в колонках:

```text
C — наименование товара магазина
F — количество / размер упаковки магазина
G — единица магазина
H — ручная цена магазина
I — цена магазина от парсера
J — ручная рабочая цена за единицу сборника
K — рабочая цена от парсера
L — URL или текстовое описание источника
M — учтён для парсинга
N — дата обновления парсинга
O — дата ручной цены
P — справочная информация
```

Эти данные относятся преимущественно к:

```text
supplier_offers
```

---

### 29.9. Наименование товара поставщика

Колонка:

```text
C — Наименование магазина
```

по фактическому содержимому НЕ является названием магазина.

В ней хранится конкретное наименование товара у поставщика.

Поэтому:

```text
C
→ supplier_offers.product_name
```

---

### 29.10. Количество и единица поставщика

Колонки:

```text
F — количество / упаковка
G — единица магазина
```

переносятся в:

```text
supplier_offers.supplier_quantity
supplier_offers.supplier_unit
```

Оба поля допускают `NULL`.

Это важно, потому что в старой базе существуют корректные URL поставщиков без заполненного количества товара.

Наличие URL НЕ означает, что `supplier_quantity` обязательно известно.

## 29.11. Четыре разных вида цены

Анализ `МАТ ГЭСН` показал, что необходимо отдельно хранить четыре цены.

### Цена товара магазина

Excel:

```text
H — цена магазин
```

PostgreSQL:

```text
supplier_offers.source_price
```

Это цена непосредственно той упаковки или единицы товара, которая указана у поставщика.

---

### Цена товара от парсера

Excel:

```text
I — цена магазин (парсинг)
```

PostgreSQL:

```text
supplier_offers.last_parsed_source_price
```

Это последняя цена непосредственно карточки товара, полученная автоматически.

---

### Подтверждённая рабочая цена

Excel:

```text
J — Цена за ед измерения сборника
```

PostgreSQL:

```text
supplier_offers.approved_price
```

Это рабочая цена, приведённая к единице измерения базы.

---

### Рабочая цена от парсера

Excel:

```text
K — Цена за ед измерения сборника (парсинг)
```

PostgreSQL:

```text
supplier_offers.last_parsed_price
```

Это цена из парсера после приведения к единице измерения базы.

---

### Итоговая схема цен

```text
Цена сайта вручную

│
└── source_price
        │
        └── пересчёт
                │
                └── approved_price
                    J


Цена сайта из парсера
I
│

        │
        └── тот же смысл пересчёта
                │
                └── last_parsed_price
                    K
```

## 29.12. Пересчёт цены

В старом Excel нет одной универсальной формулы пересчёта.

Встречаются, например:

```text
=H
=H/F
=H*D
=H/F*D
=H/F*1000
=H*1000
=H*40
=H/2.5
=H*0.8*1000
```

и многие другие варианты.

Поэтому V3 хранит не только единицы измерения, но и информацию о логике пересчёта.

---

### 29.13. conversion_factor

Существующее поле:

```text
supplier_offers.conversion_factor
numeric(18,8)
NOT NULL
DEFAULT 1
```

используется как основной коэффициент пересчёта.

Базовая формула:

```text
working_price =
source_price * conversion_factor
```

Пример:

```text
source_price = 1019
approved_price = 679.3333

conversion_factor ≈
679.3333 / 1019
≈ 0.66666667
```

---

### 29.14. conversion_offset

Для формул, содержащих дополнительное слагаемое, добавлено:

```text
supplier_offers.conversion_offset
numeric(18,4)
NOT NULL
DEFAULT 0
```

Например старая формула:

```text
=H+775
```

может быть представлена:

```text
conversion_factor = 1
conversion_offset = 775
```

и рассчитана:

```text
working_price =
source_price * conversion_factor
+ conversion_offset
```

---

### 29.15. conversion_mode

Добавлено поле:

```text
supplier_offers.conversion_mode
text
NOT NULL
DEFAULT 'factor'
```

Оно определяет способ формирования рабочей цены.

Планируемые значения:

```text
factor
factor_offset
manual
legacy_formula
```

#### factor

Обычный линейный пересчёт:

```text
price * conversion_factor
```

#### factor_offset

Пересчёт с дополнительным слагаемым:

```text
price * conversion_factor
+ conversion_offset
```

#### manual

Цена установлена вручную и не должна автоматически пересчитываться по неизвестной логике.

#### legacy_formula

Строка использовала сложную историческую Excel-формулу, которую нельзя безопасно заменить обычным коэффициентом.

---

## 29.16. Сохранение исходных формул Excel

Добавлены:

```text
supplier_offers.conversion_formula
supplier_offers.parsed_conversion_formula
```

### conversion_formula

Хранит исходную формулу Excel из колонки J.

Пример:

```text
H23/1.5
```

или:

```text
H177/F177*D177
```

### parsed_conversion_formula

Хранит исходную формулу Excel из колонки K.

Формулы J и K хранятся отдельно, потому что они не всегда совпадают буквально.

Например в старой базе используется универсальная формула:

```text
IF(
  OR(H="", I="", J="", H=0),
  "",
  ROUND(I*J/H, 2)
)
```

которая применяет к новой парсинговой цене отношение:

```text
J / H
```

### Важное ограничение

Price Control V3 НЕ должен выполнять содержимое:

```text
conversion_formula
parsed_conversion_formula
```

как произвольный программный код.

Эти поля нужны для:

- исторического хранения;
- проверки миграции;
- диагностики;
- ручного анализа сложных строк;
- последующего безопасного преобразования в внутреннюю модель V3.

---

## 29.17. Сложные и повреждённые старые формулы

В старом Excel существуют отдельные формулы:

- со ссылками на другие листы;
- со ссылками на колонку P;
- с дополнительными константами;
- с повреждёнными `#REF!`;
- с ошибочными операторами;
- с формулами, возвращающими логические значения;
- с формулами, не связанными напрямую с H.

Примеры:

```text
H*(D/F)+'Пот'!D15
H*2.777+'Пот'!D63
H*P
IFERROR(VLOOKUP(#REF!,#REF!,1,FALSE),"")
```

Такие формулы НЕ должны автоматически исполняться сервером V3.

Для них используется:

```text
conversion_mode = legacy_formula
```

или:

```text
conversion_mode = manual
```

в зависимости от результатов импорта.

## 29.20. supplier_id теперь допускает NULL

Первоначально:

```text
supplier_offers.supplier_id
```

был:


```text

```

изменила:

```text

NOT NULL
```

на:

```text
supplier_id
NULLABLE
```

Внешний ключ на таблицу:

```text

```

при этом сохраняется.

Если `supplier_id` заполнен, он обязан ссылаться на существующего поставщика.

## 29.28. Определение поставщика по URL

В исходной базе используются как основные, так и региональные домены.

Например один поставщик может иметь:

```text
ekb.saturn.net
msk.saturn.net
sam.saturn.net
chel.saturn.net
...
```

Поэтому правило:

```text
один hostname = один supplier
```

использовать нельзя.

Для V3 потребуется отдельная логика сопоставления доменов с поставщиками.

Пример:

```text
*.saturn.net
→ SATURN

*.petrovich.ru
→ PETROVICH

*.metallprofil.ru
→ METALLPROFIL
```

Конкретный справочник соответствий должен быть сформирован перед полноценной миграцией предложений.

## 29.29. Колонка P — «Справка»

Колонка:

```text
P — Справка
```

содержит разнородную техническую информацию.

Примеры:

```text
1л=0,8кг
1 м³ = 1000 л
цена за ед. без ндс
масса упаковки
дополнительные пояснения пересчёта
```

На текущем этапе данные P нельзя потерять.

До окончательного определения уровня хранения они должны сохраняться как историческая информация.

Для значений, относящихся к конкретному товару или пересчёту поставщика, предпочтительным местом является:

```text
supplier_offers.notes
```

Если информация относится непосредственно к самому материалу независимо от поставщика, она может быть перенесена в:

```text
materials.notes
```

Импортёр не должен автоматически распределять неоднозначный текст без явного правила.

## 29.31. Что нельзя делать при импорте

Импортёр НЕ должен:

- объединять строки только потому, что у них одинаковый код;
- придумывать отсутствующее наименование;
- автоматически заменять повреждённую цену на 0;
- заменять ошибочную дату текущей датой;
- считать текст `средняя цена` URL;
- автоматически включать парсинг для текстового источника;
- удалять строки с неполным количеством поставщика;
- исполнять старые Excel-формулы как JavaScript;
- изменять исходный Excel;
- останавливать весь импорт из-за одной повреждённой строки.
